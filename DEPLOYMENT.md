# Deploying MotoConnect

Everything below is on a free plan. Where a free tier has a sharp edge, it is
named rather than glossed over.

| Piece | Where | Cost |
| --- | --- | --- |
| Consumer app + ops console | Vercel (static) | Free |
| API + WebSocket + sweeper | Render (web service) | Free |
| Postgres + PostGIS | **Neon** | Free |
| Rider ID photographs | **Cloudflare R2** | Free |
| Admin setup emails | Postmark | Free tier |

**Nothing here needs a human to wake it up, and no uptime pinger is required.**
Render sleeps after 15 minutes idle and cold-starts in about a minute when
someone opens the app. Neon's compute scales to zero after 5 minutes idle and
resumes on the next connection in milliseconds. Both wake themselves.

**Why not Supabase.** A free Supabase project pauses after 7 days of inactivity
and needs a manual click in the dashboard to restore. Neon does not: suspension
is automatic and so is resumption. That single difference is why the database
moved.

**Why the API is not on Vercel.** It holds persistent WebSocket connections for
rider pool pushes and live ride tracking, and it runs a sweeper that expires
60-second claim windows. Serverless functions can do neither. Vercel hosts the
two front ends, which it is excellent at.

## 1. Neon — the database

1. Create an account at [neon.com](https://neon.com) and a project. Pick the
   region closest to Rwanda (`aws-eu-central-1`, Frankfurt).
2. Name the database `motoconnect`.
3. **Enable PostGIS.** Open the SQL Editor and run:

   ```sql
   CREATE EXTENSION IF NOT EXISTS postgis;
   ```

   The migration issues this too, but running it first surfaces any permission
   problem immediately rather than mid-deploy. PostGIS is not optional — rider
   matching runs `ST_DWithin` radius queries against `geography(POINT, 4326)`.
4. Copy the **pooled** connection string from Connect. It looks like:

   ```
   postgres://<user>:<password>@ep-xxxx-pooler.eu-central-1.aws.neon.tech/motoconnect?sslmode=require
   ```

   Use the *pooled* one (with `-pooler` in the host). TLS is switched on
   automatically by the app for any non-localhost database.

### Run the migration

From your laptop, pointed at Neon:

```bash
cd server
DATABASE_URL="postgres://<user>:<password>@ep-xxxx-pooler.eu-central-1.aws.neon.tech/motoconnect?sslmode=require" \
  npm run db:migrate
```

Both migration files are safe to re-run: the base schema is applied only to an
empty database, and the ops-console schema is idempotent by construction. The
API also runs migrations on every start, so this first manual run is really just
a way to see the output.

Do **not** run `npm run db:seed` against production — it inserts fictional
riders and passengers.

## 2. Cloudflare R2 — rider ID photographs

Render's free plan has **no persistent disk**, so images written to local disk
are destroyed on every deploy — silently, because the database rows survive and
point at files that no longer exist. R2 fixes that: 10 GB free, zero egress
charges, no expiry.

1. Cloudflare dashboard → **R2** → Create bucket → name it `rider-documents`.
   Leave the location automatic.
2. **Do not** connect a public `r2.dev` URL or a custom domain to this bucket.
   Buckets are private by default and must stay that way — it holds photographs
   of national ID cards. The app reads them server-side with API keys and serves
   them only through an authenticated admin route that logs every view.
3. R2 → **Manage API tokens** → Create API token → permission **Object Read &
   Write**, scoped to this bucket. Copy the Access Key ID and Secret Access Key
   — the secret is shown once.
4. Note your **Account ID** from the R2 overview page.

Cloudflare may ask for a payment method when you first enable R2. The free
allowance still applies; nothing is charged unless you exceed it.

## 3. Render — the API

1. New → **Blueprint**, point it at this repository. Render reads `render.yaml`
   and creates the service with `rootDir: server`.
2. Fill in the variables marked `sync: false`:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon pooled connection string |
   | `R2_ACCOUNT_ID` | Cloudflare account ID |
   | `R2_ACCESS_KEY_ID` | R2 API token access key |
   | `R2_SECRET_ACCESS_KEY` | R2 API token secret |
   | `POSTMARK_SERVER_TOKEN` | Postmark **Server** token |
   | `EMAIL_FROM` | A verified Postmark sender, e.g. `MotoConnect Ops <ops@yourdomain.rw>` |
   | `WEB_ORIGINS` | `https://<your-vercel-domain>,https://ops.<your-domain>` |
   | `ADMIN_ORIGIN` | `https://ops.<your-domain>` |
   | `ADMIN_CONSOLE_URL` | `https://ops.<your-domain>` |

   `JWT_SECRET` is generated by Render automatically. Do not set it by hand.

3. Deploy. Watch the logs — the server refuses to start in production if a
   required secret is missing, and prints exactly which one.

On first boot against an empty database it creates the seed `super_admin`
(`byiringirinnocent8@gmail.com`) with **no password** and emails a one-time
setup link. If Postmark is not yet working, the link is printed in the Render
logs instead, and the log says plainly that it was not delivered.

### Postmark

Two settings decide whether that link ever arrives:

- `POSTMARK_SERVER_TOKEN` must be the **Server** token (Servers → your server →
  API Tokens), not the Account token. The account token fails with ErrorCode 10.
- `EMAIL_FROM` must be a verified Sender Signature or on a verified domain, or
  Postmark rejects the send with ErrorCode 400.

Both are translated into plain language in the logs rather than surfacing as a
bare number.

## 4. Vercel — the two front ends

1. New Project → import this repository. `vercel.json` supplies the build; leave
   the framework preset alone.
2. Environment variables:

   | Variable | Value |
   | --- | --- |
   | `VITE_API_URL` | `https://<your-render-service>.onrender.com` |
   | `VITE_GOOGLE_MAPS_API_KEY` | Your Maps key, restricted to your domains |

   `VITE_API_URL` must have **no trailing slash**. It is used for both REST and
   the WebSocket. A Vercel rewrite cannot proxy a WebSocket upgrade, which is
   why the front end talks to Render directly and `WEB_ORIGINS` on the API side
   has to list the Vercel domains.

3. Deploy. One build produces both bundles: `index.html` (consumer) and
   `admin.html` (ops console).

### Putting the ops console on its own subdomain

The spec asks for the console on a separate host that is never linked publicly.

1. Vercel → Settings → Domains → add `ops.yourdomain.rw` to the same project.
2. `vercel.json` already contains a host-conditional rewrite: any request whose
   host starts with `ops.` serves `admin.html`. Nothing else is needed.
3. `admin.html` is also served at `/admin` on the main domain as a fallback,
   and carries `X-Robots-Tag: noindex, nofollow, noarchive`.

After the domain is live, set `ADMIN_ORIGIN` and `ADMIN_CONSOLE_URL` on Render
to `https://ops.yourdomain.rw` and redeploy, so setup links point at the right
place and the admin API only answers that origin.

## 5. Sleeping — why nothing needs babysitting

Both halves sleep, and both wake themselves:

| | Sleeps after | Wakes on | Needs a human? |
| --- | --- | --- | --- |
| Render (API) | 15 min idle | The next HTTP or WebSocket request, ~1 min | No |
| Neon (database) | 5 min idle | The next connection, milliseconds | No |

The first person to open the app after a quiet spell waits roughly a minute for
Render. Everyone after that sees normal speed. There is **no uptime pinger to
set up and nothing to click**.

If you later decide that first-visitor minute is unacceptable, a free check at
[cron-job.org](https://cron-job.org) hitting
`https://<your-service>.onrender.com/health` every 10 minutes keeps Render warm.
Render allows 750 instance-hours a month and a month is about 730, so staying
awake permanently just fits — but it would also hold Neon's compute awake, which
eats the compute allowance described below. Leaving both asleep is cheaper and
is the recommended setting.

### Staying inside Neon's compute allowance

Neon's free plan gives **100 CU-hours per project per month** — about 400 hours
at the smallest compute size. A naive 5-second sweeper would hold the database
awake for every minute the API is running and burn straight through that.

So the sweeper adapts (`server/src/services/sweeper.ts`): it ticks every 5
seconds while rides are in flight, and drops to 60 seconds when nothing is
open, at which point it runs a single cheap existence check instead of the full
sweep. The connection pool empties, Neon scales to zero, and the clock stops. A
new ride request wakes it instantly, because the sweeper subscribes to ride
events rather than discovering them by polling.

At pilot volumes this keeps compute use far below the cap. If you outgrow it,
Neon's paid tier starts at pay-as-you-go with no monthly minimum.

## 6. First sign-in to the ops console

1. Open the setup link (from your inbox, or from the Render logs).
2. Choose a password — 12 characters minimum, and a passphrase beats
   punctuation.
3. Sign in. You will be required to enrol an authenticator app: 2FA is
   mandatory for `super_admin`, because that account can issue refunds and ban
   users.
4. Add your other operators in Settings → Add admin. `support` is view-only on
   rides, users and disputes; `finance_ops` handles payments, subscriptions and
   refunds but cannot touch verification or bans. Each gets their own setup
   link — you never choose anyone else's password.

If a setup link expires, reissue it from Settings, or from your laptop:

```bash
cd server && npm run db:seed:admin -- --resend
```

## What is still not production-ready

**Consumer phone login does not work in production.** There is no SMS gateway,
so verification codes are written to the server log and sent to nobody. The API
prints this warning on every production boot, and `request-otp` now returns an
honest error instead of pretending a code was sent.

This is the one remaining launch blocker, and it costs money whichever way you
go:

- Firebase Phone Auth needs the Blaze plan with a billing account — there has
  been no free SMS allowance on Spark since September 2024.
- Twilio, Africa's Talking and Infobip all price per message.
- A local Rwandan aggregator such as Pindo or Mista is usually cheapest for
  +250 numbers and is worth pricing first.

Wiring one up is a single function: implement `deliver()` in
`server/src/services/smsService.ts` and set `SMS_PROVIDER`. Everything else —
code generation, hashing, expiry, attempt limits, rate limiting — is already
built and tested.

The **ops console is unaffected** and fully usable today, because it
authenticates with email and password rather than SMS.

Two other things are deliberately off:

- **Refunds** are recorded but not paid out automatically (`PAYPACK_REFUND_ENABLED=false`).
  See the README for why no provider exposes a usable reversal.
- **PayPack** runs in test mode until `PAYPACK_CLIENT_ID` and
  `PAYPACK_CLIENT_SECRET` are set. Subscriptions activate without money moving.

## Free-tier ceilings worth watching

| Limit | Free allowance | What happens at the edge |
| --- | --- | --- |
| Neon storage | 0.5 GB per project | Project suspended for writes — **data is not deleted** |
| Neon compute | 100 CU-hours/month | Compute suspends until the next month — **data is not deleted** |
| Neon transfer | 5 GB/month | Throttled |
| R2 storage | 10 GB | ≈17,000 riders at 3 photos each; the 365-day purge reclaims space |
| R2 egress | Unlimited, free | Nothing — this is R2's whole point |
| Render instance hours | 750/month | Service suspended until the next month |
| Postmark | 100 emails/month on the free tier | Setup links stop sending |

Neon's own wording is worth quoting, because it is the reassuring part: *"None
of these limits delete your data. Compute resumes when the next monthly window
opens or you move to a paid plan."* Hitting a ceiling costs you availability,
never the database.

The document retention purge runs nightly and deletes ID photographs 365 days
after a verification decision, which is what keeps storage from growing without
bound. Confirm that figure against Rwandan data-protection guidance before you
go live — it is a placeholder, not legal advice.
